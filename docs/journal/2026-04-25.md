### VRAM constraint findings

M620 has 1997 MiB total / ~1969 MiB free. Findings:

- **Embed 0.6B Q8_0**: full GPU offload fits at ctx ≤512 (KV+compute buffer ~500 MiB)
- **1.7B Q8_0**: full offload at default ctx 4096 OOMs (compute buffer alone wants 1.2 GiB on top of model). Strategies: small ctx (`-c 1024` or less), or partial offload (`-ngl 16` of 28 layers), or quantized KV cache (`--cache-type-k q4_0`)
- **8B Q4_K_M**: 4.7 GB model alone exceeds VRAM. CPU-primary with KV cache GPU offload only

Per memory S174, this matches the 2GB workload strategy already designed.

### GPU sharing — `-ngl 0` is not enough

First L1 boot crashed with:

```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 862.98 MiB on device 0: cudaMalloc failed: out of memory
ggml_gallocr_reserve_n_impl: failed to allocate CUDA0 buffer of size 904900608
graph_reserve: failed to allocate compute buffers
status=11/SEGV
```

llama.cpp built with `GGML_CUDA=ON` always tries to allocate the compute buffer on `CUDA0` regardless of `-ngl 0`. Embed already had ~1.1 GB pinned. L1's 862 MiB compute buffer didn't fit.

**Fix:** `Environment="CUDA_VISIBLE_DEVICES="` in the unit. Hides the GPU from the process entirely. After re-deploy both L0 + L1 stable, listening on 8001/8002.

### Qwen3 reasoning model — backend integration note

L0 chat completion returned `message.content = ""` and `message.reasoning_content = "..."`. Qwen3 puts chain-of-thought in a separate field. `local_client.py` (P2-06) must:

- Parse `reasoning_content` and either drop it or surface it as a separate field on `AgentResult`
- For non-reasoning prompts, use `enable_thinking=false` in the chat template (Qwen3 docs) to skip CoT
- For tool-use, watch for `<tool_call>` blocks in `content`

This is not a bug in our setup — it's standard Qwen3 behavior. Document in `docs/model_tiers.md` when wiring P2-06.
